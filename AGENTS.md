# Agent instructions

This is a dotfiles repo for the `portatilmanu` machine (ASUS ROG Flow X13 running Manjaro i3).

**Important: The workspace root `/home/manu343726/` is the real `$HOME` of this machine — not a cloned repo in a project directory. Git was init'd directly in `~` to track dotfiles, with `.gitignore` set to `/*` by default so only explicitly whitelisted files are tracked.**

## Rules

0. **Follow protobuf RPC design patterns.** Before designing or modifying any `.proto` file, read `~/dotfilesd/docs/proto-design.md`. Use enums for option sets, `repeated` for multi-value fields (never comma-separated strings), and sub-messages for grouping. Load the `proto-design` skill when working on proto files.

1. **Always commit and push changes to both remotes.** After modifying any tracked file (dotfiles, daemon source, CLI source, docs, etc.), stage and commit with a descriptive message, then push. The `origin` remote has two push URLs — GitHub (`git@github.com:Manu343726/portatilmanu-dotfiles`) and the internal LAN server. A plain `git push` pushes to **both**. Always verify the push succeeds.

2. **Read docs first.** Before doing any work, read `~/dotfilesd/README.md` and `~/dotfilesd/docs/` for context. Follow the development guide in `docs/development.md`.

3. **NEVER run shell commands with `sudo`.** The agent runs in a non-interactive shell; `sudo` triggers a password prompt that the agent cannot answer, and failed attempts will lock the sudo session. Use the `exec_run` MCP tool with `sudo: true` instead — it asks the user for the password through a secure feedback channel, then passes it to `sudo -S` without exposing it to the agent.

4. **Check `.agents/skills/`** for project-specific skills before working. Load any relevant skill with the skills tool.

5. Keep changes idempotent — reloading configs should work cleanly.

6. Follow the Monokai palette (`#272822` bg, `#A6E22E` accent, etc.) when adding visual configs.

7. **Always use the Makefile for building — never `go build`/`go run` directly.** Running `go build .` inside a plugin directory produces a binary that gets accidentally committed and pushed. Instead:
   - **Daemon/CLI:** use `make build` then `make install`.
   - **Plugin:** use `make plugin-build PLUGIN=<name>` (this compiles proto first, then builds to `~/.cache/dotfilesd/plugins/<name>/<name>` — outside the source tree).
   - **Plugin proto:** use `make plugin-proto PLUGIN=<name>`.
   - After modifying a plugin, run `make install` (restarts the daemon) or reload plugins manually.
   - Generated protobuf code (`*.pb.go`, `*connect/*.connect.go`, `*_docs.go`, `*_doc.pb`, `**/proto/**/*.md`), docs artifacts, and ELF binaries are all gitignored. Never `git add` them.

8. **Use the dotfilesd daemon for dotfiles operations.** The daemon runs as a systemd user service and exposes:
   - **MCP** via `dotfilesctl mcp` stdio — for AI agents (tools: `system_ping`, `system_info`, `system_sudo`, `dotfiles_status`, `dotfiles_git`, `exec_run`, `config_reload`).
   - **Connect RPC** at `http://127.0.0.1:9105` — accessible via the `dotfilesctl` CLI client (`~/dotfilesd/cmd/dotfilesctl/main.go`).
   - Use `exec_run` with `sudo: true` for privileged commands — the daemon asks the user for the password securely via the feedback system.
   - After modifying daemon/client code, run `make install` and restart the daemon if needed.
   - See `~/dotfilesd/docs/` for full daemon documentation.

9. **After a sudo session times out, the user will be prompted for their password again the next time `exec_run(sudo=true)` is called.** This is expected behavior — the agent does NOT need to call `sudo -k` or any reset command. The daemon re-requests auth via elicitation (or pkexec/terminal) each time sudo is needed and `sudo -S` fails. If `pkexec` is used instead of elicitation, `pkexec` caches credentials in its own session (15-minute PAM timestamp), so repeated sudo calls within that window won't prompt again. The agent should just silently retry the same `exec_run(sudo=true)` call — the user will be prompted through the appropriate feedback channel (MCP elicitation form, pkexec dialog, or terminal).

10. **Udev rule override at `/etc/udev/rules.d/60-nvidia.rules`.** The system nvidia package installs `60-nvidia.rules` that calls `nvidia-modprobe` on GPU bind, which auto-loads nvidia modules. This conflicts with supergfxctl in Integrated mode, causing a udev-worker to hang in D-state and block shutdown. An empty override file exists at `/etc/udev/rules.d/60-nvidia.rules` to disable this. If reinstalling, recreate it: `sudo tee /etc/udev/rules.d/60-nvidia.rules <<<'# Intentionally empty: see AGENTS.md'`.

11. **TLP power tuning — per-profile.** Power profile switching uses TLP (via `~/.local/bin/power-profile`, bound to `$mod+Ctrl+p`), controlled without root through `tlpctl` (the `tlp-pd` D-Bus client) — not `tlp` (needs root). TLP has 3 profiles, each with its own parameter set (suffix `_AC`/`_BAT`/`_SAV` maps to performance/balanced/power-saver respectively). The per-profile config lives in `/etc/tlp.d/profiles.conf` (system file, not in this repo — recreate on reinstall), which declares the default profile per power source:
   - **Pluggled in (AC)** → `performance` profile (full speed, uncapped: `CPU_BOOST_ON_AC=1`, `CPU_SCALING_MAX_FREQ_ON_AC=4785000` — see caveat below, `governor=performance`, `PLATFORM_PROFILE_ON_AC=performance`) — set via `TLP_PROFILE_AC=PRF`.
   - **On battery** → `power-saver` profile (aggressive 1 GHz cap: `CPU_BOOST_ON_SAV=0`, `CPU_SCALING_MAX_FREQ_ON_SAV=1000000`, `governor=powersave`, `PCIE_ASPM` powersupersave, `PLATFORM_PROFILE_ON_SAV=quiet`) — set via `TLP_PROFILE_BAT=SAV`. This keeps all-core load power flat (~8 W idle floor dominated by screen/WiFi/SSD).
   - **balanced** profile is deliberately left at TLP's light defaults (`PLATFORM_PROFILE_ON_BAT=balanced`), but it *does* pin `CPU_SCALING_MAX_FREQ_ON_BAT=4785000` for the reason below.
   After editing, apply with `sudo tlp start`. **Caveat (root cause found 2026-10-17): `CPU_SCALING_MAX_FREQ_ON_AC=0` is NOT "unlimited" — `tlp-func-cpu` skips the write entirely when the value is `0`** (`[ -n "$maxfreq" ] && [ "$maxfreq" != "0" ]`), so a 1 GHz cap left by `power-saver` survives every later profile switch. Symptom seen that day: `tlpctl get` → `balanced` while on AC, `scaling_max_freq` stuck at `1000000`, CPU idling at 964 MHz — Moonlight stuttered badly. Fixes now in place: both `_AC` and `_BAT` pin the hardware max (`4785000`, confirmed via `cat /sys/devices/system/cpu/cpu*/cpufreq/cpuinfo_max_freq`), so any profile switch resets the cap. If it ever sticks again, release it with `echo 4785000 > /sys/devices/system/cpu/cpu*/cpufreq/scaling_max_freq` (or reboot), and check that `tlpctl get` says `performance` while on AC — if it says `balanced`, something ran `tlpctl set`/a UPower `PowerProfiles` client manually.
    **Recurrencia 2026-10-28 — el mismo cuadro otra vez, y no era la red:** el stream a PCGORDO volvió a ir lento con `tlpctl get` → **`power-saver`** estando `AC0 online=1`, y `journalctl` mostrando `Run detached TLP to apply profile 'power-saver'` a las 21:12. Las 16 CPUs a **964 MHz**, `boost=0`, EPP `power`, `platform_profile=quiet`. Arreglado con `tlpctl set performance` (vía `exec_run(sudo=true)`): quedó `performance`/`performance`/`boost=1`/EPP `performance` y los núcleos a 2.9–3.7 GHz. **Antes de culpar a la red, lee siempre esas cinco cosas** (`tlpctl get`, `scaling_cur_freq`, `cpufreq/boost`, EPP, `platform_profile`), porque el síntoma (tirones con la red perfecta) es idéntico al de las reglas 20/21/22.
    **Cómo leer las frecuencias, para no "corregir" el `4785000`:** con `amd-pstate` en `active`, `scaling_max_freq` no pasa del nominal (**3201000** en el 6800HS) y el turbo lo lleva `cpufreq/boost`; con `boost=0`, `cpuinfo_max_freq` **también** lee `3201000`, y con `boost=1` lee `4785000`. Es decir, el valor de `CPU_SCALING_MAX_FREQ_ON_AC/BAT` es correcto — el `3201000` que se ve con el perfil `power-saver` es el nominal sin boost, no un error de configuración.
    This machine is normally in **Integrated** GPU mode (supergfxctl) so the NVIDIA dGPU is fully off; don't re-enable unless needed.

   **asusd config** (`/etc/asusd/asusd.ron`): asusd's platform_profile switching is disabled (`change_platform_profile_on_ac/battery: false`) so TLP fully owns the platform profile. asusd still manages fan curves (`fan_curves.ron`), PPT power limits, keyboard backlight, and charge threshold. The ASUS platform supports only `quiet balanced performance` (not `low-power` which TLP uses as default for `PLATFORM_PROFILE_ON_SAV`, so it's overridden to `quiet`).

   **Daemon plugins**: The `resources` and `tmuxbar` plugins read the TLP power profile via `collectPowerProfile()` (calls `tlpctl get`), exposed as `PowerProfile` enum (`PERF/BAL/SAV`) in the protobuf API. The tmuxbar's `power-profile-widget` displays the current TLP profile in the status bar. The rofi menu at `$mod+Ctrl+p` uses `tlpctl get/set` (script: `~/.local/bin/power-profile`).

   **Critical battery → hibernate** (UPower, separate from TLP): `/etc/UPower/UPower.conf` sets `CriticalPowerAction=Hibernate` so the machine hibernates (not suspends) when the battery hits 2%. `HandleLidSwitch=hibernate` in `/etc/systemd/logind.conf` covers lid-close **on battery** (hibernate, to preserve running state across a long unplugged period). Closing the lid **while plugged in / charging must do nothing**: `HandleLidSwitchExternalPower=ignore` in the same file enforces that — do not revert it to `suspend`. Reload with `sudo systemctl kill -s HUP systemd-logind` (SIGHUP, not restart). xfce4-power-manager runs with `logind-handle-lid-switch = true` so logind is the sole actor on lid-close; don't fix lid behavior there. See `.docs/power.md` for the full config and reinstall steps.

14. **In Pangolin, rename every `niceId` to the service's own name — never leave a generated one.** Pangolin Cloud mints `niceId` values like `mundane-rufous-rat-kangaroo` and `delightful-thirteen-lined-ground-squirrel`. Set them to `authentik`, `homelab`, etc.

15. **Every service is published through Pangolin on the `homelab` site, behind Pangolin SSO. No exceptions.**
    - **One site.** Every target binds to the site named `homelab` (`siteId 26999`). Nothing gets published to another site, and nothing gets a direct `ports:` publish to the internet as a shortcut.
    - **Authentik is the only identity system.** Pangolin authenticates the request through `pangolin_org_idp`, which delegates to Authentik over OIDC. Do not add `pangolin_resource_user`, `pangolin_resource_password`, per-resource PIN codes, or a second user store — the access model lives in Authentik's groups and is consumed as one Pangolin role.
    - **`public = false` on every service**, which sets `sso = true`. So the apps carry no OIDC configuration of their own: Pangolin terminates the session and proxies an already-authenticated request. Configuring a second OIDC client inside LiteLLM or LibreChat would mean two login forms in one flow, which is a bad experience and buys nothing.
    - **The one exception is Authentik itself** (`public = true`, `sso = false`), and it is structural rather than a preference: it is what Pangolin delegates authentication *to*, so Pangolin's own login in front of it would demand a credential from a system that cannot issue one. It is the only entry in `services` allowed to be `public = true`.
    - **Publishing a service means two terraform entries, not one.** A `pangolin_resource` with no target answers nothing; the `pangolin_target` is what binds `site_id` + `ip` + `port`. Verify both: `sso: true`, a target on site `homelab`, and `reachable: true` in `tofu output resources`.

Each stack's compose file is responsible for its own LAN-side protection; do not assume Pangolin covers it.

The client's DNS proxy then falls back to `1.1.1.1`, so every estate name answers the *public* IP: the split-brain needs a query from a LAN address, and one that arrives through the tunnel is not one (that is the "split brain DNS doesn't work on Ethernet" symptom). Two things to remember about it: it must **recompute on every dispatcher event, not only on `up`** — a route is device-bound and dies with its device, so on 2026-10-15 the home WiFi took the `/32` over from the dock's Ethernet and then went down, taking the route with it while the Ethernet never fired another `up` (it logs transitions to `journalctl -t homelab-lan-route`, and `pangolin-client.service` also calls it from `ExecStartPre`); and **NetworkManager must keep a real resolver to fall back on** (`ipv4.ignore-auto-dns no` on the home profiles — the home DHCP option 6 is Pi-hole), because the system resolver *is* the client's own proxy, so stopping or restarting the client otherwise deadlocks DNS, with the client unable to resolve `pangolin.manu343726.com` to start again. Verify with `ip route get 192.168.0.30` (must say the Ethernet interface, not `pangolin`). Details in [`.docs/pangolin-client.md`](.docs/pangolin-client.md). The **server-side** counterpart (the site advertising `172.24.0.1`, the Docker bridge, as its endpoint, which left the site on `Relay` and Vaultwarden unreachable) was caused by the homelab VM's **rootless** Docker: `rootlesskit --port-driver=builtin` rewrites the source address of every incoming connection and never propagates UDP source addresses, which WireGuard needs. **Fixed 2026-10-14** with `DOCKERD_ROOTLESS_ROOTLESSKIT_PORT_DRIVER=slirp4netns` (propagates TCP *and* UDP) in `~/.config/systemd/user/docker.service.d/20-source-ip-transparent.conf` on the VM, plus a daemon restart and a restart of `pangolin-site-selfhosted.service`. It is documented in the `homelab` repo (`docs/pangolin-site-endpoint-detection.md`); don't re-diagnose it from the laptop.

If the vault tools fail, check that the portátil holds a **valid** `LITELLM_MCP_KEY` first — a stale one answers `401` on *every* gateway MCP, which reads like the vault being broken (it happened on 2026-10-17).
    - **Secret fields are redacted by default** (`reveal: true` to show them). The account master password sits in the gitignored `.env`, so treat that file as the crown jewels.

18. **Bluetooth audio to the SMSL AD18: never leave a 2.4 GHz WiFi radio next to the amp — read [`.docs/bluetooth-audio.md`](.docs/bluetooth-audio.md) before debugging BT audio again.** The X13 has no dedicated BT radio: it is a **MediaTek MT7922 combo** (WiFi `mt7921e` PCIe + BT USB `13d3:3568`) sharing one front-end, so BT competes with its own WiFi; keep the laptop's WiFi on **5 GHz**. The 2026-10-14 outage (continuous stuttering + a disconnect every ~30 s) was the **2.4 GHz radio of the AP sitting next to the AD18** desensitising the amp's BT receiver: `btmon` showed the **amp itself** terminating the ACL (`Remote User Terminated Connection 0x13`) after `ACL packet for unknown connection handle 3837` garbage arrived. Proven A/B: same AP, 2.4 GHz off → 0 failures; AP back with only 5 GHz (ch48, full signal) → still 0 failures. Watch the trap: "turning off the band" in the AP's UI does not always silence it — a half-applied setting left residual emission and the cuts continued; a full power cycle fixed it. Verify with `nmcli -f BSSID,SSID,CHAN,SIGNAL dev wifi list` (the AP's 2.4 GHz BSS must be absent). Besides that, the tracked `~/.config/wireplumber/wireplumber.conf.d/51-bluetooth.conf` forces **SBC** instead of the default **aptX HD** (576 kbps, unsustainable against a BT 4.2 sink; note the codec list is global, so it also caps the Bose QC45) and sets `session.suspend-timeout-seconds = 0` / `node.pause-on-idle = false` because the AD18 never answers AVDTP `Suspend`. Gotchas: `bluetoothctl scan on` + `connect` in the same run always fails with `br-connection-page-timeout` (scanning blocks paging — use the blueman GUI); `btmon -a` takes a *filename* (to replay use `-r <file>`), `btmon` needs root, and the MT7922's BR/EDR RSSI readings (`-2/0 dBm`) are a driver quirk, not real link quality. The AD18 is also a **USB DAC** (`alsa_card.usb-SMSL_AUDIO_SMSL_AD18_AMP-00`) — the zero-dropout fallback.

19. **Ethernet without IPv4 = ARP flux, not DHCP — read [`.docs/lan-arp-flux.md`](.docs/lan-arp-flux.md).** The X13's USB Ethernet (`enp9s0f4u1u4`, `r8152`) and its WiFi (`wlp6s0`, MediaTek MT7922) can be on the same L2 segment (`192.168.0.0/24`) at the same time. With Linux's default weak-host ARP model (`arp_ignore=0`/`arp_announce=0`) the WiFi answered ARP for the wired DHCP address and the wired NIC emitted ARP sourced with the WiFi IP, so NetworkManager's IPv4 **ACD** (`ipv4.dad-timeout`, on by default) treated the machine's own WiFi MAC (`E8:FB:1C:14:E4:21`) as a duplicate and **withdrew the lease** during its `acd pending` phase. Symptom: the link says `connected` but carries only `fe80::` and no IPv4 at all, intermittently (`ipv4.may-fail=yes` hides the failure); the router does hand out `192.168.0.100`. Diagnosis is `journalctl -b -u NetworkManager | grep "conflict detected"` — if the host MAC belongs to your own other NIC, it is this. Fixed 2026-10-17 with `/etc/sysctl.d/99-arp-flux.conf` (`all`/`default` `arp_ignore=1`, `arp_announce=2`; `all` is enough because the kernel takes `max(all, iface)` and per-interface lines would error for a USB NIC that may be absent at boot). **Do not "fix" it by disabling ACD** (`ipv4.dad-timeout=0`) unless you also accept the WiFi answering ARP for the wired IP; that is only the fallback.

20. **USB autosuspend on the USB-C Ethernet is a latency/drop source — keep it excluded in every TLP profile.** Diagnosed 2026-10-18 while chasing Moonlight stutter: the RTL8153 (`0bda:8153`, `enp9s0f4u1u4`) sits behind a hub (`2109:0817`) and TLP's default `USB_AUTOSUSPEND=1` puts both in autosuspend. Symptoms on a silent gigabit LAN: TCP RTT to the host jumping from 0.35 ms to 10-21 ms in bursts, `rx_dropped` creeping up, and Moonlight reporting "Slow connection to PC / frames dropped by your network connection" with 400-900 ms video stalls. Two layers now enforce it, because **the udev rule alone is not enough — TLP re-applies autosuspend on every profile change**:
    - `/etc/udev/rules.d/61-usb-eth-no-autosuspend.rules` sets `power/control=on` on both devices on add (covers the first plug-in, before TLP runs).
    - `/etc/tlp.d/profiles.conf` carries `USB_DENYLIST="0bda:8153 2109:0817"`. `USB_DENYLIST` is **not** profile-suffixed, so TLP honours it in `performance`, `balanced` and `power-saver` alike.
    Verify with `for d in 9-1 9-1.4; do cat /sys/bus/usb/devices/$d/power/control; done` (must say `on` after any `tlp start`/profile switch) and by re-measuring `curl -sk -o /dev/null -w '%{time_connect}' https://192.168.0.29:47990/` (flat ~0.4 ms, no spikes). This is **separate** from the encoder-side findings: when the Moonlight host's game drops to 6-12 fps (BAR's *Limit idle FPS* widget, 6 fps when its window is unfocused) or when the client asks for far more bitrate than the host's VBR encoder produces, Moonlight shows the same "slow connection" warning over a perfect network.

21. **Moonlight must run on the NVIDIA dGPU, never on the Radeon iGPU — `~/.local/bin/moonlight` is a wrapper that enforces it.** In **Hybrid** mode both the internal panel (`card1-eDP-1`) and the external monitor (`card1-DP-2`) hang off the AMD iGPU, so stock Moonlight picks the Radeon for Vulkan *and* VAAPI. The Rembrandt VCN tops out near 500 Mpix/s while 2560x1440 at 120-144 fps needs 440-530 Mpix/s, so the decoder queue overflows: the client log fills with `Video decode unit queue overflow` / `IDR frame request sent` / `Unrecoverable frame N: x+y=z received < n needed` and the stream stutters — with a *perfect* network (0 packet loss, 0.4 ms RTT, no socket backlog). Meanwhile the RTX 3050 idles at 0 %.
    - The wrapper exports `LIBVA_DRIVER_NAME=nvidia`, `NVD_BACKEND=direct`, `__NV_PRIME_RENDER_OFFLOAD=1`, `__GLX_VENDOR_LIBRARY_NAME=nvidia` and execs `/usr/bin/moonlight`; it is skipped when `/dev/nvidia0` is absent or `supergfxctl -g` says `Integrated`, so Integrated mode still works untouched. Since `~/.local/bin` precedes `/usr/bin` in `PATH`, dmenu/i3 launches go through it.
    - It needs **`libva-nvidia-driver`** (extra, 0.0.18) so VAAPI is backed by NVDEC; without it Moonlight can only decode with VAAPI on the AMD VCN. Verify with `nvidia-smi` (RTX 3050 active) and Moonlight's log: `Driver: VA-API NVDEC driver [direct backend]` + `Vulkan rendering device selected: NVIDIA GeForce RTX 3050 Laptop GPU`.
    - **Codec matters as much as the GPU**: Apollo's logs from May show `h264_nvenc`, but today it negotiated `hevc_nvenc` (Apollo 0.4.6, "HEVC P1 async two-pass rfi"), and HEVC on the AMD VCN is far slower. With HEVC the client logged ~1330 `Unrecoverable frame` lines; forcing H.264 (Moonlight → Video codec → H.264, or `--video-codec H.264`) took it to 0 even on the iGPU. Moonlight's codec setting lives in the GUI config; the config file has no key until it is set.
    - **La conexión a PCGORDO va SIEMPRE por ZeroTier (`172.25.209.143`), nunca por la LAN — no es un desvío que haya que "arreglar".** Está decidido así desde hace tiempo: es la misma ruta dentro y fuera de casa, y por eso el host de Moonlight apunta al túnel. El conf vive en `~/.config/Moonlight Game Streaming Project/Moonlight.conf` (ojo, con espacios) y guarda la dirección por entrada (`1\localaddress`); si aparece `192.168.0.29` es que se conectó por LAN y hay que devolverlo a `172.25.209.143`. La interfaz ZT tiene **MTU 1350** y el cliente manda `packetsize=1200`, que es lo correcto. En esta ruta, antes de sospechar del túnel comprueba que es P2P directo y limpio (`ping -s 1200` al host ≈ 0.5-1 ms, 0 % pérdida; el underlay debe ser el cable, no WiFi) y que `rx_dropped` de `ztyxa6ggpt` y los `skmem` `d0` de los sockets de Moonlight están a cero.

22. **PCGORDO's Realtek NIC: the Moonlight stutter was the *host's* send path dropping whole UDP batches — read this before re-diagnosing.** Diagnosed 2026-10-18 after a long hunt where every client-side and network metric was clean (0 packet loss at the tap, 0 NIC drops, 0 socket backlog, NVDEC + NVIDIA render, GPU idle). The smoking gun is in Apollo/Vibepollo's own log:
    ```
    Warning: WSASendMsg() batch failed: 10035; packets=20; bytes=24320; ... batch was not sent
    Warning: Video frame send aborted: frame=24979; block=0; packets accepted in failed batch=0
    ```
    `10035` is `WSAEWOULDBLOCK`: the UDP send buffer filled and the server **discarded the whole batch**, so frames reached the client incomplete, Moonlight asked for IDR after IDR, and the user saw 0.3-0.9 s freezes *with zero measurable packet loss* — because the packets were never sent, not lost in transit. It looked like a network fault because the same stalls appeared over both Ethernet and WiFi, and because a synthetic UDP stream (which paces smoothly instead of bursting whole frames) did not reproduce it.
    - The NIC is a **Realtek Gaming 2.5GbE** with the usual Realtek power-saving defaults on, which is what throttled the egress. All three now disabled (persistent in the adapter's registry), plus flow control off and a bigger Winsock send window:
      ```
      Set-NetAdapterAdvancedProperty -Name Ethernet -RegistryKeyword EnableGreenEthernet -RegistryValue 0
      Set-NetAdapterAdvancedProperty -Name Ethernet -RegistryKeyword GigaLite           -RegistryValue 0
      Set-NetAdapterAdvancedProperty -Name Ethernet -RegistryKeyword PowerSavingMode    -RegistryValue 0
      Set-NetAdapterAdvancedProperty -Name Ethernet -RegistryKeyword '*FlowControl'     -RegistryValue 0
      # HKLM:\SYSTEM\CurrentControlSet\Services\AFD\Parameters -> DefaultSendWindow (DWORD) = 1048576
      Restart-NetAdapter -Name Ethernet
      ```
      `DefaultSendWindow` only applies to **sockets created after** the change, so the streaming server must be restarted (or the client must reconnect) for it to take effect.
    - Verified on 2026-10-18 20:50+: video flow went from 26.8 Mbps with gaps up to 805 ms (12 gaps >250 ms per 60 s) to **109 Mbps with a 56.9 ms max gap and zero gaps >100 ms**, and the `WSASendMsg 10035` warnings stopped. A Realtek driver update may reset these five settings — re-check them first if the stutter returns.
    - Things that were **not** the cause, despite looking like it (all reverted or harmless): Apollo 0.4.6 replacing Vibepollo (reinstalled 2.0.1), USB autosuspend on the portátil's USB-C Ethernet (still worth keeping off, rule 20), ZeroTier vs LAN, HEVC vs H.264, and the game's own frame rate.
    - **Re-chequeado 2026-10-28, con el stutter de vuelta: la NIC estaba bien.** Los cinco ajustes seguían en 0 / 1048576, el driver Realtek seguía en la versión de 2024 (nadie lo actualizó), y en el `sunshine-*.log` de ese día había **0** `WSASendMsg`/`10035`/`batch failed` — ni una en los 10 días posteriores al arreglo, frente a las 28 del 18-10. Ese día la causa fue el perfil de energía del portátil (regla 11). Antes de volver a mirar la NIC, confirma en el log que el patrón ha reaparecido: sin esas líneas, el problema no está en el envío del host.

23. **Delegate the work to subagents; the main session orchestrates.** Every unit of work in this repo goes out to a subagent — a diagnosis, a file edit, a live fix, a document, a commit — with one bounded workstream per subagent (`subagent`, `background: true`), briefed with the paths it needs, the facts already measured and where they came from, the exact deliverable, and what it must not touch. The main session keeps the thread and two duties that never delegate: **the verification** (a subagent's report is a claim, not a measurement — re-measure it before repeating it to the operator) **and the record** (the board, the docs, the commit). Running the work in the main session is the failure mode this rule exists for: it spends the orchestrator's context re-reading what it already knows and leaves nobody holding the whole picture. The operational detail — how to brief, how to split, how to verify, what collides — is the `orchestration` skill (`~/.agents/skills/orchestration/SKILL.md`).
